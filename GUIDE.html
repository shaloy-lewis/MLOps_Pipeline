MLOps Pipeline
E-Commerce Purchase Prediction

A complete production-grade ML system built in pure Python — no MLflow, no DVC, no cloud. Every concept is implemented from scratch: validation, versioning, drift detection, retraining, and serving. The goal is to show what these production tools actually do before you add them.

Problem Statement

Business context

An e-commerce retailer collects session-level data on every visitor — pages viewed, time spent, bounce and exit rates, whether the visit falls near a special day, and so on. Most visitors leave without buying. A small fraction complete a purchase. The business wants to know, at the end of a session, whether that visitor was a buyer — so it can score batches of sessions, identify patterns, and decide where to direct marketing spend.

ML problem definition

DimensionDefinition
TaskBinary classification
InputOne row per browsing session — 18 features: page counts, durations, bounce/exit rates, PageValues, Month, VisitorType, SpecialDay, Weekend
OutputPredicted label: Revenue = 1 (purchase) or Revenue = 0 (no purchase), plus a purchase probability score
Target variableRevenue — boolean, converted to int. Positive class = session ended in a purchase
Class distribution~12–15% positive (buyers). Strong imbalance — the majority class is always "no purchase"
Primary metricF1 score on the minority class (buyers). Accuracy is misleading at this imbalance ratio
Inference modeBatch scoring — sessions are scored as a batch after accumulation. A REST endpoint (serve.py) is also provided for on-demand single-session scoring

Why this is hard

A model that predicts "no purchase" for every session achieves 87% accuracy and catches zero buyers. The real challenge is the class imbalance: the minority class (buyers) is what the business cares about entirely, but it is the harder class to learn. A naive model optimised for accuracy will systematically ignore it.

The secondary challenge is distribution shift. The model is trained on sessions from February to October — normal shopping behaviour. It is then deployed into the holiday season (November–December), where purchase intent, page engagement, and session patterns all shift significantly. A model without monitoring will degrade silently.

The Situation

This project simulates a realistic deployment timeline. The data arrives in two phases, matching how data actually accumulates in production.

Phase 1 — Training
February → October
7,317 sessions. All the data the team has. The model is trained, validated, and deployed before the holiday season.
Phase 2 — Live Traffic
November → December
4,725 sessions arrive post-deployment. Used for drift monitoring and batch scoring — not for training.
Phase 3 — Retrain Decision
Late November onward
Drift triggers fire. Ground truth labels accumulate. Retraining is evaluated and executed with a chosen strategy.

It is October. The data science team has 7,317 sessions from February to October. The model must be built and deployed before the holiday season begins. November and December data is not yet available — it will arrive as live traffic after the model goes live.

Business Cost Model

The choice of evaluation metric follows directly from the cost of each type of error. This is not an academic choice — it determines which model gets deployed.

Missed Buyer (False Negative)
$85
Wasted Offer (False Positive)
$3
Cost Ratio FN : FP
28 : 1

A model that misses a buyer costs 28× more than one that wastes an offer on a non-buyer. This ratio directly shapes the pipeline:

  • Primary metric: F1 on the minority class (buyers) — not accuracy
  • Class imbalance handling: scale_pos_weight = n_negative / n_positive ≈ 7.1
  • Deployment gates: F1 ≥ 0.65, Recall ≥ 0.60, AUC-PR ≥ 0.60, AUC-ROC ≥ 0.85
  • Drift Rule 1: any high-importance feature shift triggers immediate retrain consideration

A model with 88% accuracy that predicts "no purchase" for every session misses every buyer. On a test batch of 1,463 sessions with ~180 actual buyers, that is $15,300 in missed revenue — invisible unless you look past the accuracy number.

Quick Start

Install dependencies

pip install -r requirements.txt

Run in order

python baseline.py          # See what goes wrong without MLOps discipline
python model_selection.py   # Rigorous model comparison — select the winner
python main.py              # Build and deploy the production pipeline
python retrain.py --dry-run # Evaluate drift — should we retrain?

After retraining (pick one strategy)

python retrain.py --strategy mixed          # recommended for seasonal drift
python retrain.py --strategy finetune       # fast warm-start
python retrain.py --strategy reexperiment   # full hyperparameter search

Serve the model

uvicorn serve:app --reload --port 8000      # REST API — open /docs
python batch_infer.py                       # score the Nov-Dec batch CSV
python plot_logs.py                         # HTML log visualizer — opens in browser

Step 2 — model_selection.py

Context: Still October. The senior team runs a proper model comparison before building anything.

The evaluation framework is defined before any model runs: primary metric is F1 on the minority class (buyers), same stratified 80/20 split for all models, same imbalance handling, same preprocessing.

Step 3 — main.py

Context: October. All 12 stages run in sequence. The model is trained on Feb–Oct data and deployed at the end.

Pipeline Stages

Stage 0
Initialisation
Sets random seed (42) and creates the directory structure. Seed is critical: same data + same seed = same model every run.
Stage 1
Data Loading
Loads data/train.csv (Feb–Oct, 7,317 rows) and data/current.csv (Nov–Dec, 4,725 rows). The Nov–Dec data is loaded for monitoring only — it is not used for training.
Stage 2
Data Validation
Checks schema, null rates, value ranges, and categorical domains before any model sees the data. Hard failures abort the pipeline. Soft warnings are logged.
Stage 3
Feature Engineering
One-hot encodes Month and VisitorType (nominal, not ordinal). Imputes missing values using training-set medians, saved to models/feature_pipeline.json. At inference time, the same medians are loaded — not recomputed. This prevents training-serving skew.
Stage 4
Train/Test Split — Pre-Deployment Validation
Splits the Feb–Oct data 80/20 with stratify=y. Both splits contain 12.3% buyers. The hold-out 20% is never touched during training — it is the pre-deployment quality gate.
Stage 5
Model Training
Trains LightGBM on the 80% split. scale_pos_weight = n_negative / n_positive ≈ 7.1 — every false negative is penalised 7× more than a false positive, matching the $85/$3 business cost ratio.
Stage 6
Pre-Deployment Evaluation
Evaluates on the 20% hold-out only. Expected: F1 0.67–0.76, Recall 0.69–0.78, AUC-ROC 0.92–0.96, AUC-PR 0.72–0.80. Slice evaluation by VisitorType and Month reveals performance gaps.
Stage 7
Deployment Gates
Hard thresholds: F1 ≥ 0.65, Recall ≥ 0.60, AUC-PR ≥ 0.60, AUC-ROC ≥ 0.85. If any gate fails, the pipeline stops. The model is not registered or served.
Stage 8
Experiment Tracking
Appends the run's parameters and metrics to logs/experiments.csv. Every run is logged with a timestamp — the full history of all training runs is preserved.
Stage 9
Model Registry
Saves the model as models/model_YYYYMMDD_HHmmss_f1_X.XXX.pkl. Promotes it: candidate → staging → production. Only production-status models are served by serve.py.
Stage 10
Post-Deployment Drift Monitoring
The model is now live. Compares incoming Nov–Dec feature distributions against the Feb–Oct training baseline. Expected: PageValues +34%, ProductRelated +48%, BounceRates +16%, ExitRates +12% — all flagged as drift.
Stage 11
Batch Scoring
Scores all 4,725 post-deployment sessions using the training-time feature pipeline (saved medians) — not the inference batch statistics. Logs predictions and latency.
Stage 12
Lineage Recording
Records a full provenance snapshot in logs/lineage.json: model file, data files (with checksums), Python version, library versions, and git commit.

Step 4 — retrain.py

Context: Late November. The model has been live for ~4 weeks. 4,725 post-deployment sessions have accumulated. Ground truth labels are available.

Four Trigger Rules

RuleConditionWhy
Rule 1 Any high-importance feature drifts PageValues, BounceRates, ExitRates, ProductRelated drive >60% of feature importance. One shift = model is stale.
Rule 2 ≥ 2 features drift One noisy column might be transient. Two simultaneous drifts is almost certainly a real shift.
Rule 3 F1 drops > 5pp from baseline Even without feature drift, concept drift can degrade performance. If F1 drops, retrain regardless.
Rule 4 Last retrain < 14 days ago Prevents over-reaction to daily noise. Use --force to override.

Three Retraining Strategies

finetune

Warm-starts LightGBM: adds 150 new trees on top of the existing 500, trained only on Nov–Dec data.

Best for: mild drift, tight compute budget

Risk: may lose Feb–Oct patterns (catastrophic forgetting).

mixed  ⭐ recommended

Pools 50% of original Feb–Oct data with 100% of Nov–Dec data. Trains a fresh model from scratch.

Best for: seasonal drift — model must work on both normal and holiday traffic
reexperiment

Runs a hyperparameter grid search (4 configs) on the combined dataset. Picks best by F1, then reruns the full pipeline.

Best for: F1 has degraded significantly — original hyperparameters may be stale
